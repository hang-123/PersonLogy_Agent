# P10：基于最小记录原子的审计、监控与记录架构

## 1. 文档定位

本文将 P10 收敛为一项可独立建设的平台能力：以“最小记录原子”为统一事实载体，为审计、运行监控和业务记录提供可靠采集、存储、查询与追踪能力。

P10 不建设新的通用日志平台，也不替代现有业务数据库、日志系统或指标系统。它只负责统一关键事实的记录方式，并向三类使用场景提供标准化数据。

## 2. P10 的核心结论

P10 只保留以下四个核心子模块：

1. **记录原子协议**：定义一条记录必须表达的事实及其字段、版本和数据分级。
2. **可靠采集与写入**：负责校验、补全、幂等、重试、顺序和补偿，保证记录不静默丢失。
3. **审计与查询服务**：提供不可随意修改的审计证据、对象时间线、链路查询和导出能力。
4. **监控与运营视图**：从记录原子派生指标、告警和看板，监控业务链路及 P10 自身健康度。

三类消费链路统一使用同一记录原子：

```text
业务服务 / 管理后台 / 定时任务
              │
        记录原子 SDK
              │
      校验、补全、幂等、写入
              │
 ┌────────────┼────────────┐
 │            │            │
审计证据     业务记录     监控指标
```

## 3. 范围与边界

### 3.1 纳入范围

- 用户认证、权限和角色变化；
- 核心业务对象的创建、修改、删除和恢复；
- 数据查看、导出、下载等高风险行为；
- 异步任务的开始、完成、失败和重试；
- 外部接口调用及其结果；
- 关键链路的成功率、延迟、积压和失败情况；
- 记录完整性、丢失率和存储容量监控。

### 3.2 暂不纳入

- 替换现有应用日志平台；
- 记录所有 DEBUG 日志和普通运行日志；
- 建设通用数据湖或完整数据仓库；
- 在 P10 内实现业务审批、工单或权限管理本身；
- 为每个业务字段建立独立的审计模型；
- 首期覆盖全部历史数据。

## 4. 最小记录原子

### 4.1 定义

最小记录原子是系统中一件可独立识别、可追踪、可校验的事实，回答以下问题：

> 谁，在什么时间，通过什么来源，对什么对象执行了什么动作，结果如何？

### 4.2 建议字段

| 字段 | 说明 |
|---|---|
| `record_id` | 全局唯一记录 ID，建议 UUIDv7 |
| `record_type` | 事件类型，如 `document.exported` |
| `schema_version` | 记录结构版本 |
| `occurred_at` | 事实实际发生时间 |
| `ingested_at` | 平台接收时间 |
| `tenant_id` | 租户或业务域 |
| `trace_id` | 链路追踪 ID |
| `request_id` | 请求、任务或批次 ID |
| `actor` | 操作者、服务账号或系统主体 |
| `subject` | 被操作对象 |
| `action` | 执行动作 |
| `result` | 成功、失败、拒绝或部分成功 |
| `source` | 来源服务、版本和客户端 |
| `payload` | 必要的业务扩展数据 |
| `classification` | 数据敏感级别 |
| `retention_policy` | 留存策略 |
| `prev_hash` / `hash` | 防篡改校验字段，可按分区建立 |
| `parent_record_id` | 父记录或关联记录 |

### 4.3 设计约束

- 记录原子只表达一件最小事实，不把整段日志作为原子。
- 业务字段放入 `payload`，平台字段保持稳定。
- 密码、Token、完整身份证号等敏感内容不得进入原子。
- 关键事件必须具备 `trace_id`、`request_id` 或等价关联标识。
- 记录默认追加写入，不通过业务接口直接修改原始记录。
- 修正错误采用追加修正记录，不覆盖原始事实。
- 每个事件类型必须有责任服务、Schema 版本和留存策略。

## 5. 四个子模块的落地设计

### 5.1 记录原子协议

职责：统一事件结构、命名、版本和数据分级。

交付内容：

- JSON Schema 或 Protobuf Schema；
- 事件类型目录；
- 字段白名单和敏感字段规则；
- Schema 版本兼容策略；
- SDK 使用规范和接入模板。

事件命名采用“对象.动作”形式，例如：

```text
user.login
user.permission_changed
document.created
document.exported
task.completed
data.deleted
```

### 5.2 可靠采集与写入

职责：确保关键记录能够被稳定接收、去重、存储和补偿。

实现要求：

- 事务型业务操作优先使用 Outbox 或等价机制；
- 异步任务通过消息队列或事件总线传输；
- 支持幂等键、重试、死信、顺序控制和积压监控；
- P10 故障时业务可异步降级，不因审计写入短暂失败而整体不可用；
- 恢复后支持积压记录自动补偿。

### 5.3 审计与查询服务

职责：保存审计证据，支持责任追踪和历史还原。

实现要求：

- 审计原始记录采用追加写入和独立权限；
- 支持按租户、操作者、对象、动作、时间、结果和 `trace_id` 查询；
- 支持对象时间线和请求时间线；
- 支持审计导出和完整性验证；
- 所有查询、导出和权限变更自身也产生审计记录；
- 审计查询权限与普通业务查询权限分离。

### 5.4 监控与运营视图

职责：从记录原子派生运行指标，并监控 P10 自身质量。

首期指标：

- 事件吞吐量；
- 业务操作成功率和失败率；
- 请求、任务和处理延迟；
- 队列积压和处理延迟；
- 记录丢失、重复和非法事件数量；
- 关键字段缺失率；
- 存储容量、查询量和成本；
- P0/P1 高风险事件数量。

监控不直接依赖各服务重复埋点，而是优先从记录原子统一派生，保证指标口径一致。

## 6. 开发落地计划

### 阶段一：边界确认与事件目录

周期：2～3 个工作日

工作项：

- 核对现有日志、审计、指标、链路追踪和消息基础设施；
- 确定首批 2～3 个核心服务；
- 建立高价值事件清单；
- 完成数据分级、留存和责任人确认；
- 明确 P10 与现有系统的职责边界。

交付物：事件目录、字段清单、现状差距清单、MVP 范围说明。

### 阶段二：原子协议与 SDK

周期：1 周

工作项：

- 完成 Schema、命名规范和版本策略；
- 开发 SDK，封装字段补全、脱敏、校验和幂等键；
- 建立本地测试工具和 Schema 校验流程；
- 为首批事件提供接入模板。

交付物：协议文档、Schema、SDK、接入示例和测试用例。

### 阶段三：可靠写入链路

周期：1～1.5 周

工作项：

- 建立采集入口和事件分流；
- 接入 Outbox 或消息队列；
- 实现重试、死信、幂等、积压和补偿；
- 建立 P10 写入链路自身的运行监控。

交付物：采集服务、存储适配、失败补偿机制、链路监控看板。

### 阶段四：审计查询与对象时间线

周期：1 周

工作项：

- 建立审计追加存储；
- 实现统一查询 API；
- 实现对象时间线、请求时间线和审计导出；
- 增加查询脱敏、限流和查询审计。

交付物：审计 API、查询页面或管理端接口、导出和校验能力。

### 阶段五：监控、告警与灰度接入

周期：1～2 周

工作项：

- 从记录原子派生核心指标；
- 建立 P0/P1/P2 告警规则；
- 接入认证权限、核心对象变更、数据导出和异步任务；
- 完成故障、重复提交、消息丢失和权限绕过测试；
- 根据灰度结果修正 Schema 和采集策略。

交付物：监控看板、告警规则、首批服务接入报告、上线复盘记录。

## 7. MVP 验收标准

MVP 不要求覆盖全部业务，但必须完成一条完整闭环：

```text
产生记录 → 可靠写入 → 审计查询 → 对象/链路还原 → 指标派生 → 异常告警
```

上线门槛：

| 类别 | 指标 |
|---|---|
| 覆盖率 | 首批核心操作记录覆盖率不低于 99% |
| 可靠性 | 关键记录不静默丢失，重复消息不造成重复业务结果 |
| 可追踪性 | 关键事件具备链路或请求关联标识 |
| 查询性能 | 常用审计查询 P95 不高于 3 秒 |
| 告警时效 | P0/P1 事件 1 分钟内发现 |
| 数据安全 | 敏感字段无明文泄漏，查询按权限脱敏 |
| 完整性 | 原始审计记录可完成校验 |
| 可恢复性 | 故障恢复后可补偿积压事件 |

## 8. 首期建议接入顺序

1. 认证与权限模块；
2. 核心业务对象的创建、修改和删除；
3. 数据查看、导出和下载；
4. 异步任务与批处理；
5. 管理后台和外部接口调用。

首期只选择能够验证“记录—审计—监控—追踪”闭环的服务，不追求一次性全量接入。

## 9. 关键风险控制

| 风险 | 控制措施 |
|---|---|
| 事件量膨胀 | 事件分级、冷热分层和留存策略 |
| 业务与记录不一致 | Outbox、事务消息或等价补偿机制 |
| 敏感信息泄漏 | Schema 白名单、字段脱敏和上线前扫描 |
| 审计记录被覆盖 | 追加存储、独立权限和完整性校验 |
| 指标口径不一致 | 统一从记录原子派生指标 |
| P10 故障影响业务 | 异步写入、本地缓冲、重试和补偿 |
| 查询成本过高 | 原始存储与索引存储分离，限制大范围查询 |

## 10. 一句话定义

**P10 是面向关键事实的统一记录基础设施：一个最小记录原子、一个可靠写入链路、一个审计查询服务和一套由记录派生的监控视图。**
